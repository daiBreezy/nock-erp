# กฎ Negative Actions ของ erp-v2 (ลบ / หยุด / archive)

> อ่านไฟล์นี้ก่อนทำปุ่ม/การกระทำที่ "เอาออก" ทุกชนิด — ลบ, ปิด, ยกเลิก, archive, โอนงาน
> **เป้าหมาย: ทุก negative action มี logic ผูกชัดเจน + จุดให้ฉุกคิด** กันลบพลาดแล้วพัง Report/Log ตามมา
> ที่มา: เจ้าของสั่ง (2026-11-10) — "ทุกอันต้องมี logic ผูก + จุดให้ฉุกคิด เพื่อกันปัญหาตามมา"
>
> **สถานะ: ร่าง — รอเจ้าของเคาะ** (ดู §6 "4 คำถาม" ที่ใส่ default ไว้แล้ว) → เคาะเสร็จค่อย implement

---

## 1. หลักคิด — Framework เดียวทุก entity, มี 3 ทางออก

ทุก entity (นักเรียน · ครอบครัว · Staff · Course · Class · ฯลฯ) ใช้กฎชุดเดียวกัน ตัดสินจากคำถามเดียว: **"record นี้มีประวัติ/ถูกใช้ไปแล้วหรือยัง?"**

| ทางออก | ใช้เมื่อ | กลไก |
|---|---|---|
| **1. ลบจริง (hard delete)** | record **ว่างเปล่า** — สร้างลอยๆ ยังไม่มี logic อะไรผูก (ไม่มีคาบ/บิล/ประวัติ/ความสัมพันธ์) | ผ่าน **"ด่านเลข" (math gate)** ก่อนลบ → หายถาวร |
| **2. Archive (ซ่อนแต่เก็บ)** | record ที่ **เคยมีประวัติ/ถูกใช้** — ลบไม่ได้เพราะกระทบ Report/Log | ซ่อนจากลิสต์ปกติ · มีตัวกรอง "ดู Archived" · **Restore กลับมาได้** |
| **3. ไม่มีทางตัน** | ลบไม่ได้ด้วยเหตุผลใดก็ตาม | **ห้ามเป็นปุ่มเทาเฉยๆ** — บอกเหตุผลที่ลบไม่ได้ + เสนอ Archive แทนเสมอ |

### ด่านเลข (math gate) คืออะไร
จุดให้ฉุกคิดก่อนลบถาวร — ไม่ใช่แค่กด "ยืนยัน" รัวๆ:
- โจทย์เลข **บวก/ลบ เท่านั้น** · operand และผลลัพธ์เป็น **เลขหลักเดียว** (เช่น `3 + 4 = ?`, `8 − 5 = ?`)
- ตอบถูกก่อน ปุ่มลบจึงทำงาน · ตอบผิด = สุ่มโจทย์ใหม่
- จงใจให้ "ต้องหยุดอ่าน" ไม่ใช่กดผ่านด้วยกล้ามเนื้อมือ
- Component กลาง: `components/app/math-gate.tsx` (ยังไม่มี — สร้างตอน implement) ใช้ซ้ำทุกจุดที่ hard delete

## 2. กติกาต่อ entity

| Entity | ว่างเปล่า → ลบจริง (math gate) | มีประวัติ → Archive | หมายเหตุ |
|---|---|---|---|
| **นักเรียน (Student)** | ยังไม่มีคอร์ส/บิล/เช็กชื่อ | มีคอร์ส/ประวัติการเรียน/บิล | archive มีอยู่แล้ว (`archiveStudent`) — ขาดแค่ตัวกรอง + math gate ตอนลบจริง |
| **ครอบครัว (Family)** | ยังไม่มีนักเรียนผูก | มีนักเรียน (archived ก็นับ) | ⚠️ **ตอนนี้ไม่มี negative action เลย** — ต้องเพิ่มทั้ง archive + ลบ |
| **Staff** | ยังไม่มีงาน/คาบ/เอกสารผูก | เคยสอน/อนุมัติ/มีเอกสาร | archive ได้ถ้าไม่มีงานค้าง **+ ต้องมีปุ่ม "โอนงาน A→B" แยกเดี่ยว** (ดู §4) |
| **Course** | ไม่เคยถูกซื้อ | เคยขาย/มีนักเรียนลง | ลบ r22 ทำแล้ว (commit `7d4451f`) **แต่ยังไม่มี math gate — ต้องกลับมาเติม** |
| **Class** | ไม่เคยใช้ (ไม่มีคาบเกิดจริง/เช็กชื่อ) | เคยมีคาบ/เช็กชื่อ | ⚠️ `deactivateClass` ตอนนี้ **แอบ hard-ลบคาบอนาคตที่ยังไม่เช็กชื่อ** — ต้องแก้ให้เป็น soft (ดู §3) |
| **Session (คาบ)** | — | — | **ไม่มีปุ่มลบ** — "ยกเลิกคาบ" แบบ soft + เหตุผล ที่มีอยู่ถูกแล้ว (เป็นประวัติ/เช็กชื่อ ลบจะพัง Report) |
| **Invoice / Receipt / Credit Note** | — | — | ใช้ `voidInvoice` / Credit Note / Refund (บังคับเหตุผลแล้ว) — ห้ามลบเอกสารการเงิน |
| **Branch** | — | — | `setBranchActive` (ปิดสาขา) — ถือเป็น archive ของสาขา ไม่ลบ |

> **กฎเหล็ก:** ของที่กระทบ **เงิน (บิล/ใบเสร็จ)** หรือ **การเช็กชื่อ/ประวัติเรียน** — ลบจริงไม่ได้เด็ดขาด ไม่ว่าจะว่างแค่ไหน ใช้ void/cancel/archive เท่านั้น

## 3. ช่องโหว่โค้ดที่ต้องปิด (Audit 2026-11-10 — `store.ts`, `types.ts`, `customers.ts`)

เรียงตามความเสี่ยง:

1. **`deactivateClass` (`store.ts:721`) แอบ hard-ลบคาบอนาคตที่ยังไม่เช็กชื่อ** — hard delete ซ่อนในปุ่มที่ดูเหมือน soft → **แก้เป็น soft (เก็บคาบไว้ ตั้งสถานะยกเลิก + เหตุผล)** เป็นอันดับแรก เพราะอันตรายที่สุด
2. **ครอบครัว (Family) ไม่มี negative action เลย** — เพิ่ม `Family.archived:{at,by,reason}` + `archiveFamily`/`restoreFamily` + ลบจริง (ถ้าไม่มีนักเรียนผูก)
3. **archive นักเรียนแล้วหายจากลิสต์ ไม่มีตัวกรองดู Archived** (`customers.ts:36` กรองทิ้ง) — เพิ่ม `ShowChip` "ดูที่เก็บเข้าคลัง" + ปุ่ม Restore
4. **math gate ยังไม่มีที่ไหนเลย** — hard-delete ที่มีจริง (`deleteCourse` `store.ts:1166` · `deleteForm` `3076`) แค่ confirm → เติม math gate ทุกจุด
5. **Staff/Course/Class ใช้แค่ `active:boolean`** ไม่มี metadata ว่าใคร/เมื่อไหร่/ทำไม → ยกระดับเป็น `archived:{at,by,reason}` แบบเดียวกับ Student (ดู §6 Q1)
6. **โอนงาน Staff ผูกใน `deactivateStaff(id, replacementId)` (`store.ts:1110`)** — ยังไม่มีปุ่มโอนแยกเดี่ยว → แยกออกมา (ดู §4)
7. negative อื่นที่ **มีและบังคับเหตุผลแล้ว (ไม่ต้องแก้ แค่รักษามาตรฐาน):** `voidInvoice`, Credit Note/Refund, `removeStudentFromClass/Session`, `cancelTrip`, `setBranchActive`, `cancelTeacherDay`

## 4. โอนงาน Staff A→B (ปุ่มแยกเดี่ยว)

A ลาออก/ย้าย → ต้องส่งต่องานให้ B ก่อน archive ไม่ให้งานค้างกลางอากาศ

- ปุ่ม **"โอนงาน"** แยกจากปุ่ม archive/ปิด (ไม่ฝังใน `deactivateStaff`)
- เลือกผู้รับ B (staff คนเดียว หรือหลายคนแยกตามประเภทงาน — ดู §6 Q4)
- **ขอบเขตที่โอน (default: โอนทั้งหมด — ดู §6 Q4):** คาบอนาคตที่สอน · คลาสที่รับผิดชอบ · สรุปการเรียนที่ค้าง · นักเรียนในความดูแล · งาน/แจ้งเตือนที่จ่อถึง A
- โอนผ่าน `validateClass` / conflict engine เดิม — ถ้า B ชนเวลา = บอกทีละเคส ไม่โอนเงียบ
- โอนเสร็จ → **เสนอ archive A (ไม่ auto)** เพราะการออกอาจชั่วคราว (ดู §6 Q4)
- ทุกการโอนบันทึก log + `report()` toast

## 5. UX มาตรฐานของ negative action (ให้เหมือนกันทุกที่)

1. **ปุ่มลบ/ปิด อยู่ใน `⋯` (PanelMore) เสมอ** ไม่ใช่ปุ่มเด่นในแผง (ตาม [[erp-v2-panel-structure]])
2. ลบจริง → เปิด `math-gate.tsx` (โจทย์เลข) · Archive → ขอเหตุผลสั้น (ดู §6 Q2)
3. ลบไม่ได้ → **ไม่ปุ่มเทา** แต่โชว์เหตุผล 1 บรรทัด + ปุ่ม "เก็บเข้าคลังแทน" (Archive)
4. ทุก action คืน `Result {ok|error}` ผ่าน `report()` → มี toast เสมอ (ห้าม action เงียบ — ตาม CLAUDE.md ข้อ 2)

6. ข้อความไทยทั้งหมด · เพิ่มคำใหม่ใส่ TH/EN/JA ใน i18n-dict (ตาม [[erp-v2-translate-every-page]])

## 6. 4 คำถามรอเจ้าของเคาะ (ใส่ default ของผมไว้แล้ว)

> เคาะได้เลยบนร่างนี้ — เห็นด้วยกับ default ข้อไหนข้ามได้, ไม่เห็นด้วยบอกข้อนั้น

### Q1 — รวม "inactive / ปิดขาย / ปิดคลาส" กับ "Archived" เป็นสถานะเดียวไหม?
**Default ที่แนะนำ: ✅ รวมเป็นสถานะเดียว — "เก็บเข้าคลัง (Archived)"**
เหตุผล: ตอนนี้มีหลายคำที่ความหมายคล้ายกัน (`active:false`, "ปิดขาย", "ปิดคลาส") → ผู้ใช้สับสนว่าต่างกันยังไง. รวมเป็น `archived:{at,by,reason}` อันเดียวทุก entity, มี reason เป็นตัวบอกบริบท ("ปิดการขาย", "ครูลาออก" ฯลฯ). ลิสต์ default ซ่อน archived, chip เดียว "ดูที่เก็บเข้าคลัง" ใช้ได้ทุกหน้า.

### Q2 — math gate ใช้กับ hard-delete ทุก entity เหมือนกันหมด? Archive ต้องมี remark หรือแค่ confirm?
**Default ที่แนะนำ:**
- **hard delete:** math gate **เหมือนกันหมดทุก entity** (โจทย์เลขหลักเดียว ชุดเดียว) — การลบถาวรเป็นเรื่องเดียวกัน ไม่ต้องมีหลายระดับให้จำ
- **Archive:** **ต้องมีเหตุผลสั้น** (dropdown เหตุผลสำเร็จรูป + ช่องพิมพ์เสริม) ไม่ใช่แค่ confirm — เพราะ archive เปลี่ยนสิ่งที่คนอื่นเห็น/กระทบ Report แม้กู้คืนได้ · เหตุผลช่วยตอน Restore ว่าทำไมเคยเก็บ

### Q3 — สิทธิ์: ใครลบจริง / archive / restore ได้?
**Default ที่แนะนำ (ผูกกับ `permissions.ts` เดิม — `inBranch`/`crossBranch`):**
- **ลบจริง (hard delete):** **Manager ขึ้นไป** เท่านั้น (ของว่างเปล่าก็ยังเป็นการลบถาวร)
- **Archive / Restore:** **Admin ขึ้นไป** ในสาขาตัวเอง · ข้ามสาขา = **Area Manager ขึ้นไป**
- **ครู/driver:** ทำ negative action ที่เป็นโครงสร้าง (ลบ/archive นักเรียน/คอร์ส/staff) ไม่ได้ — ทำได้แค่ action ในงานตัวเอง (ยกเลิกคาบของตัวเอง + เหตุผล)

### Q4 — โอนงาน Staff: โอนเฉพาะคลาสที่สอน หรือรวมทุกอย่าง? โอนเสร็จ archive A อัตโนมัติไหม?
**Default ที่แนะนำ:**
- **โอนทุกอย่างที่ผูกกับ A** (คาบอนาคต + คลาสที่รับผิดชอบ + สรุปค้าง + นักเรียนในดูแล + งาน/แจ้งเตือนจ่อถึง) — เลือกผู้รับ B ได้ทีละประเภทงาน (default คนเดียวทั้งหมด, กดแยกผู้รับได้ถ้าต้องการ)
- **ไม่ archive A อัตโนมัติ** — โอนเสร็จแล้ว **เสนอ** archive (ปุ่มเด่นในหน้าสรุปการโอน) เพราะการออกอาจชั่วคราว/ยังมีเอกสารต้องอ้าง A; ให้คนตัดสินกดเอง

## 8. หมายเหตุการ implement (โมเดลข้อมูล)

- **`Archived = { at, by, reason }`** (`types.ts`) — metadata กลางของสถานะ "เก็บเข้าคลัง" ทุก entity. Student มีอยู่แล้ว; เพิ่มให้ **Family · Staff · Course · Klass**.
- เพื่อไม่รื้อ filter เดิมหลายสิบจุด: `active:false` ยังอยู่เป็น "ตัวสะท้อน" — **archive = set `active:false` + `archived:{…}`** พร้อมกัน, **restore = `active:true` + `archived:undefined`**. ลิสต์เดิมที่กรอง `active` ทำงานเหมือนเดิม, ตัวกรอง "ดูที่เก็บเข้าคลัง" เช็ก `archived`.
- ตาม Q1 (รวมสถานะ): ของ Course ปุ่ม "ปิดขาย" เดิม = "เก็บเข้าคลัง" (ต้องมีเหตุผล) — คำเดียวทั้งแอป.
